### Phase 10 — Business-Rule, Groundedness & Adjudication Validation

Status: complete, tested, corpus-validated, including two real bugs found via the actual corpus run and fixed with regression tests.

- **Architecture**: `pipeline/validation.py` — one small, independently-testable check function per concern (never one giant validator): `check_schema`, `check_groundedness`, `check_required_payable_evidence`, `check_classification_consistency`, `check_supplier_buyer_consistency`, `check_master_data_validity`, `check_financial_consistency`, `check_credit_memo_consistency`, `check_tax_consistency`, `check_erp_reconciliation`. `adjudicate()` composes all of them into one `ValidationResult` (a list of typed `ValidationIssue`s, each with a `check` name, `reason`, `severity` [HARD_FAIL/WARNING], a `DeclineReason` category, and the relevant `field`). A `DeclineReason` enum (`INSUFFICIENT_EVIDENCE`, `CONFLICTING_SIGNALS`, `UNBUILDABLE_FINANCIAL_FACTS`, `NON_PAYABLE_DOCUMENT`, `DUPLICATE_OF_BOOKED_PAYABLE`, `ERP_MISMATCH_IRRECONCILABLE`, `UNSUPPORTED_AMBIGUOUS_FORMAT`, `MASTER_DATA_INVALID`, `GROUNDEDNESS_FAILURE`, `BUSINESS_RULE_VIOLATION`, `SCHEMA_VIOLATION`) gives every decline a deterministic, non-vague category rather than free-text-only messages. The old Phase 1 `pipeline/business_rules.py` stub is now a compatibility shim re-exporting from this module (mirroring the `pipeline/duplicates.py` → `pipeline/duplicate_detection.py` pattern from Phase 9).
- **Adjudication order** (documented in the module docstring and here): (1) classification, (2) extraction sufficiency, (3) groundedness, (4) master-data validity, (5) duplicate status, (6) financial model construction, (7) exact ERP reconciliation, (8) business-rule validation, (9) book or decline. Steps 1/2/5/6 already happened correctly upstream (Phases 4/5/9/7) before Phase 10 runs; rather than physically reordering an already-correct pipeline (explicitly the "smallest clean change" per the brief), `adjudicate()` is called as ONE final consolidated gate — immediately after the existing duplicate check and immediately before `result.payables.append(payload)` — performing steps 3, 4 (as an explicit re-check/safety-net on top of Phase 8's own resolution-time validation), 7 (re-checked against the same unmodified `erp.py`), and 8, in that order, and reports the FIRST hard failure encountered as the decline reason.
- **Hard gates implemented**: schema conformance (required keys, valid enums, correct nested shapes, no non-numeric values in numeric fields — never silently repaired); groundedness (every non-blank `gross_total`/`invoice_number` must be traceable to the raw OCR/embedded text, in ANY plausible locale-printed form — see bug #1 below); minimum-evidence policy (a bare total-like number alone is not enough; at least one of invoice_number/supplier_name/currency/invoice_date must corroborate that the document is genuinely a payable); classification consistency (a credit-memo classification must carry credit-memo evidence; an invoice classification needs more than one weak signal); supplier/buyer identity conflict detection; master-data existence re-check (defense-in-depth, not a second matching engine — it never attempts a new match, only re-validates IDs already resolved by Phase 8); financial consistency (no malformed/NaN/infinite numbers, currency must be present); credit-memo sign convention (positive magnitudes only); tax-rate plausibility; and the exact `erp.py` reconciliation re-check (Decimal-exact, no tolerance, same unmodified wrapper Phase 7 uses).
- **Two real bugs found by running the actual corpus, not just unit tests, and fixed with regression tests before being reported as done**:
  1. **Groundedness false negatives on non-English-locale documents**: the first version of `check_groundedness` compared the Phase-6-normalized (dot-decimal) `gross_total` against the raw OCR text verbatim — but a document printed with a comma-decimal ("400,00") or EU-thousands ("1.040,06") total would never contain the dot-decimal form, so 6 genuinely legitimate payables were wrongly declined as "ungrounded." Fixed by adding `_plausible_printed_number_forms()`, which checks a normalized value against every locale form it could plausibly have been printed in (dot-decimal, comma-decimal, EU thousands+comma-decimal, US thousands+dot-decimal) before declaring it ungrounded. 4 new regression tests added (3 positive-locale-form cases + 1 confirming a genuinely fabricated number is still correctly rejected).
  2. **`subtotal` field bypassing Phase 6 normalization**: `run.py` was writing `extracted.fields["subtotal_raw"]` directly into the schema's `subtotal` field without normalizing it, so a document with a printed subtotal like `"7,434.78"` produced a `SCHEMA_VIOLATION` the moment Phase 10's schema check correctly enforced the dot-decimal requirement AUTODRAFT_SCHEMA.md specifies — the bug was in Phase 5→7 wiring, not in Phase 10's check, which caught a real pre-existing defect. Fixed by extracting a shared `_normalize_optional(raw, normalize_fn)` helper in `run.py` (also used to de-duplicate the previously-repeated invoice_date/due_date normalization try/except blocks — reducing duplicated normalization-adjacent logic, not just fixing the bug) and routing `subtotal` through it. 3 new regression tests added directly against the helper.
- **Tests**: 35 unit tests in `tests/unit/test_validation.py` (covering all 32 STEP 10.17 categories: groundedness x5, classification consistency x4, master data x6, financial x8, credit memo x3, safety x4, plus 2 full-`adjudicate()` integration cases) + 4 regression tests for bug #1 + 11 unit tests in `tests/unit/test_validation_generalization.py` (STEP 10.19: synthetic held-out fixtures for the management-fee/tax-base pattern, ambiguous identity, multi-rate tax, "Copy Tax Invoice", conflicting-totals/irreconcilable, explicit zero-rate tax, withholding, credit memo, duplicate, missing supplier ID, ambiguous BU — none tied to any specific real document/filename) + 3 regression tests in `tests/unit/test_run_normalize_optional.py` for bug #2.

### Phase 9 — Duplicate Detection

Status: complete, tested, corpus-validated, including a real bug the corpus run itself surfaced and which was fixed with a regression test.

- **Files added**: `pipeline/duplicate_detection.py` (the real implementation); `pipeline/duplicates.py` (the old Phase 1 stub) now just re-exports from the new module for backward compatibility, per the module's own docstring explaining the supersession.
- **Five layers implemented**: (1) exact file hash (SHA-256 of raw bytes), (2) content hash (SHA-256 of whitespace/case-normalized text — catches re-saved/re-scanned copies that aren't byte-identical), (3) business-key (supplier identity + invoice_number + invoice_date + currency + gross_total — built ONLY when every field is genuinely present; a partial key returns `""`, never a key built from missing values), (4) near-duplicate text similarity (`difflib.SequenceMatcher`, explicit named threshold `NEAR_DUPLICATE_SIMILARITY_THRESHOLD = 0.92`) — advisory only, per locked policy, (5) "copy"/"duplicate"/"reprint" label detection — metadata only, never decisive alone.
